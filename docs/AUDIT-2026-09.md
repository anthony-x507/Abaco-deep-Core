# Auditoría consolidada — ABACO Deep Core

**Fecha:** 2026-09-09
**Alcance:** repo `anthony-x507/Abaco-deep-Core` + `.app` publicado (`v0.1.0-unsigned-dev`, build local firmado en curso)
**Tipo:** documento de planificación (solo lectura del código — no se modificó ningún archivo del proyecto)
**Fuentes:** auditoría de features frontend (subagente `3090ebaf`), auditoría de build/docs con addendum (subagente `db17c464`), auditoría del core Python + sync (~14.500 LOC, subagente `ac8911f3`), hallazgos propios verificados sobre el repo y el bundle empaquetado, más verificación puntual de rutas:líneas citadas. Las tres auditorías están integradas en este documento.

---

## 1. Resumen ejecutivo

El repositorio promete un producto **"ABACO Deep Core"** con features propias (upload, voz STT/TTS, navegador con grabación → skill, pairing QR, auto-update, sync Tailscale, indicador "AGENTE TRABAJANDO", marca propia). Sin embargo, la auditoría muestra que **el `.app` que se publica y descarga NO contiene ni ejecuta las features ABACO**: lo que realmente corre es el **shell DSH Desktop vanilla** (fork de dsh-desktop) con branding superficial encima. Hay **dos implementaciones paralelas muertas**: (a) `desktop/features/*` — componentes TSX/JS "de presentación pura" que según su propio `README.md` *no implementan* las features y no están conectados al bundle empaquetado; y (b) `packages/abaco-*` — paquetes JS que SÍ existen en el fork y en `node_modules` del `.app`, pero que **no están habilitados en el perfil web** que la app carga en runtime, por lo que sus plugins nunca se registran. La identidad de la app sigue siendo `DSH Desktop` (`configureAppIdentity`, `src/main/index.ts:493-506`), y el `userData` colisiona con el de DSH Desktop vanilla (`dsh-desktop`). Riesgo de producto concreto: quien descarga el `.app` ve un chat Harness vanilla sin ninguna feature ABACO, y el bundle además carece de recursos/backend Python que las features requerirían (posible app que ni siquiera arranca de forma fiable en todas las configuraciones). El código Python (`core/`) y el shell conviven en el repo pero **nunca se unen en el artefacto distribuido**.

## 3. Problemas por severidad

### P0 — El producto distribuido no es ABACO (bloqueante)

**P0-1 — El `.app` corre el shell DSH Desktop vanilla, no features ABACO.**
- `configureAppIdentity()` en `desktop/src/dsh-desktop/src/main/index.ts:493-506`:
  - `app.setName('DSH Desktop Dev')` en dev; `app.setName('DSH Desktop')` en prod (líneas 495 y 500).
  - `app.setPath('userData', join(app.getPath('appData'), 'dsh-desktop'))` — colisión deliberada con DSH Desktop real.
- El bundle empaquetado (`Contents/Resources/app`) es el fork completo sin recorte: arranca el harness vanilla con su chat estándar.
- Impacto: quien descarga el `.app` no ve ninguna feature ABACO.

**P0-2 — Los paquetes `packages/abaco-*` no están habilitados en el perfil web en runtime.**
- La app carga el perfil `dshHome/profiles/web` (`src/main/index.ts:1241`, `:2587`). No existe `profiles/web/package.json` en el repo del fork que declare los plugins `abaco-*` habilitados.
- `packages/abaco-*` (brand, voice, documents, cloud-sync, onboarding, experimental, device-identity, theme) existen como `file:` deps en `desktop/src/dsh-desktop/package.json:277-283+` y están en `node_modules` del `.app`, pero **nadie los registra** en el perfil activo.
- El parche que pretende insertarlos (`desktop/src/dsh-desktop/build/dsh-desktop.patch.yml:64-109`, sección "ABACO DEEP HARNES additions") lista `abaco-theme`, `abaco-brand`, `abaco-device-identity`, `abaco-voice`, `abaco-documents`, `abaco-cloud-sync`, `abaco-onboarding`, `abaco-experimental` — pero no se verifica que ese patch se aplique ni que el perfil resultante se empaquete.

**P0-3 — `desktop/features/*` es una capa de presentación huérfana.**
- `desktop/features/README.md` lo declara explícitamente: *"This package is **pure presentation**: it owns the buttons, the icons, and the shared color tokens. It does **not** implement the features themselves"*.
- Verificado: no hay referencias desde `src/` del fork ni desde `electron.vite.config.ts` hacia `features/upload`, `features/audio`, `features/browser`, `features/agent-status` o `features/button-bar`.
- Impacto: dos implementaciones paralelas (TSX de presentación + paquetes JS) que compiten y ninguna se entrega.

### P1 — Integridad del artefacto distribuible

**P1-1 — Recursos necesarios ausentes del `.app` (`Contents/Resources`).**
- Verificado en `build/artifacts/mac-arm64/…/Contents/Resources/`: solo `app`, `app-update.yml`, `en.lproj`, `es.lproj`, `icon.icns`.
- No hay binario/modelo Whisper, no hay core Python, no hay assets de features. Las features prometidas (STT local, sync, skills) requieren estos recursos.

**P1-2 — `build/electron-builder.dev.cjs` no declara `extraResources`/`extraFiles` ni recorte de `files`.**
- Verificado: sin entradas `extraResources`, `extraFiles` o `files:` en el config.
- No se empaqueta `core/` (Python), `sync/`, modelos de voz ni perfiles de plugins ABACO.
- Nota: el config ya tiene firma/notarización habilitada (`identity: 'Anthony Sanchez (GKPMCWHU2H)'`, `notarize: true`, `hardenedRuntime: true`), por lo que un build firmado de un bundle incompleto solo certifica la incompletitud.

**P1-3 — El parche de plugins (`dsh-desktop.patch.yml:64-109`) no tiene verificación de aplicación.**
- Sin test ni paso de build que demuestre que los `insert:` de `abaco-*` se materializan en el perfil empaquetado (ver P0-2).

**P1-4 — `pyproject.toml` roto respecto a la estructura real.**
- `[tool.setuptools.packages.find]` usa `include = ["abaco_core*"]` con `where = ["."]`, pero el código vive en `core/` (no existe paquete `abaco_core` en la raíz). El nombre del proyecto además es `abaco-deep-core` con versión `0.1.0-unsigned-dev`.
- Efecto: `pip install .` no empaqueta el core, y los imports documentados fallan.

**P1-5 — Tests que importan módulos inexistentes / paths inconsistentes.**
- `tests/smoke/test_app_starts.py:6` exige `import abaco_core`; `tests/conftest.py:32` ajusta paths "so that `import abaco_core` works" — pero no existe tal paquete (P1-4).
- `pyproject.toml` declara `testpaths = ["core/tests", "sync/tests", "tests"]`; hay `tests/integration`, `tests/smoke`, `tests/fixtures` — coherencia a verificar contra lo que realmente importa cada test.
- Riesgo: suite que no pasa o pasa en falso (tests SKIP).

### P2 — Calidad / deuda de producto

**P2-1 — Auto-update con identidad y URLs heredadas de dshdesktop.**
- `app-update.yml` empaquetado es correcto (feed genérico del repo GitHub), pero el código y tests del fork conservan URLs `dshdesktop.com` (`test/version-catalog.test.ts:13-18`, `test/release.test.ts:293,475`, `test/preset-transfer-patch.test.ts:454`).
- Sin un canal/feed propio versionado de ABACO, una actualización futura podría apuntar al producto equivocado o romper la continuidad de datos.

**P2-2 — Colisión de identidad/datos con DSH Desktop vanilla.**
- `userData=dsh-desktop` compartido (P0-1) hace que perfiles, sesiones y credenciales se mezclen con cualquier instalación DSH Desktop del equipo. Riesgo de corrupción cruzada y de "upgrade parece fresh install" invertido (se comparte todo).

**P2-3 — Dos branding/identidad en paralelo.**
- `packages/abaco-brand` + `desktop/brand/*` + CSS de `desktop/features/styles` + parche de tema: fuentes de verdad duplicadas y no reconciliadas; el resultado visible depende de cuál gane en runtime.

**P2-4 — Backend Python y shell JS nunca convergen en el artefacto.**
- `core/`, `sync/` (Python) tienen tests propios de calidad, pero no hay contrato IPC/empaquetado que los una al shell; sin esto, features como sync Tailscale o Whisper local son código muerto desde la perspectiva del usuario.

## 4. Riesgo principal de producto

> **El usuario descarga el `.app` → abre un chat Harness **vanilla** (identidad DSH Desktop) sin ninguna feature ABACO, sin sync, sin voz, sin upload propio; y en configuraciones donde el perfil/recursos no cuadran, puede ni siquiera arrancar de forma fiable.** Además, al compartir `userData` con DSH Desktop real, una instalación puede pisar los datos de la otra.

Ese es el gap que invalida la propuesta de valor actual del release descargable.

## 6. Auditoría core Python + sync

> Integra el tercer reporte (subagente `ac8911f3`, ~14.500 LOC revisadas). Esta capa (`core/` + `sync/`) es la que daría backend real a las features de la sección 2, pero hoy **ninguna de ella llega al `.app`** (sección 3) y, además, **contiene fallos críticos propios** que la invalidan incluso como backend independiente.

### 6.1 Hallazgos clave (de más a menos severo)

1. **CRÍTICO — Deadlock en uploads.** `core/uploads/storage.py:37` usa `threading.Lock()` no reentrante; `store_bytes` (`:69`) adquiere el lock y dentro llama a `_append_metadata` (`:89`) que re-adquiere el mismo lock (`:201`) → auto-deadlock (reproducido). Fix: `RLock()` o sacar `_append_metadata` del bloque.
2. **CRÍTICO — HMAC de sync determinista y público.** `sync/config.py:13,41-43` deriva el secreto con `uuid5(NAMESPACE_URL, "abaco-sync-development-secret")` (constante); `_load_or_create_secret` (`:28-38`) queda como código muerto. Cualquiera con el fuente puede forjar sobres firmados. Fix: secreto aleatorio persistido con `chmod 0600`.
3. **CRÍTICO — `updater_api.py:20` importa de `.migrations` que no existe** (solo hay `migrator.py`) → el módulo es inimportable, rompe la colección de pytest y deja ~6 tests muertos.
4. **CRÍTICO — Tests de integración = humo.** Los 8 "PASS" son tautológicos (round-trips de helpers del propio test) y hay 15 skips contra módulos inexistentes (`sync.mesh_sync`, `core.plugins`, `abaco_core`). `FakeTailscale` (168 LOC) es código muerto.
5. **ALTO — Pairing API sin auth y con escalada.** `api.py:192-321` sin `Depends` de autenticación; `devices.py:245-250` concede `read_files`/`write_files` si `device_type ∈ {mac, windows, linux}` — campo que envía el propio cliente. Sin rate-limit en mint; `X-Forwarded-For` spoofeable (`:144-152`); tokens de 30 días en claro en `/tmp`.
6. **ALTO — El QR no transporta el secret → escanear-emparejar es imposible.** `codes.py:129-164` serializa `v/host/code/endpoint/expires_at/node_id` pero **no el secret**; `verify` lo exige (`validator.py:172`).
7. **ALTO — Voice: path traversal + DoS + ruta fantasma.** `api.py:155-156`: `filename` sin `basename`/`resolve` → escritura arbitraria; `:183-196` `/stt` async ejecuta un subprocess bloqueante en el event loop → DoS; `audio_url` (`:166`) anuncia una ruta que no existe. Falta `python-multipart` en deps → 9 tests de voice fallan.
8. **ALTO — Sync no funciona.** `get_state()` crashea (glob devuelve paths completos que `path_for` rechaza); push a `http://{ip}` sin puerto (→ 80) vs. server en `8765` vs. `peer.py:28` en `7777`; `conflict_resolver.py:39-43`: con timestamps iguales gana local sin tie-break → divergencia permanente; `since_timestamp` no lo honra nadie (sin incremental; `StateVector` muerto).
9. **ALTO — `TicketCompactor.compact(force=True)` (`:227-231`)** archiva tickets *open* y vacía el ledger activo; `force` está expuesto por HTTP (`api.py:72,114-116`).
10. **MEDIO — Backups y migraciones frágiles.** `backup.py:82-86`: timestamp de 1 s + `ZipFile("w")` → 4 backups en el mismo segundo colapsan a 1 (reproducido); `migrator.py:129-136` muta in-place sin rollback real pese a que `updater_api.py:114-126` lo promete.
